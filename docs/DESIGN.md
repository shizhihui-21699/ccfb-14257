# 可否认加密磁盘（denc）设计说明

## 1. 问题定义与威胁模型

使用者过境时可能被强迫交出电脑口令。目标是提供一个加密容器：

- 交出**外层口令**后，对方面对一套内容自洽、看起来正常的"诱饵"资料；
- 真正的资料存放在同一容器的**隐蔽卷（hidden volume）**里；
- 对方即使拿到整块磁盘做字节级取证，也**无法证明**存在第二份资料。

这在密码学上称为**可否认加密（plausibly deniable encryption）**。

### 威胁对手的能力

| 对手能力 | 本设计是否覆盖 |
|---|---|
| 拿到容器文件，做静态字节统计 | 覆盖 |
| 强迫交出一个口令并检查其打开的卷 | 覆盖 |
| 多次拍下磁盘快照并逐扇区对比 | **部分覆盖**（见 §7 根本局限） |
| 检查文件大小、稀疏区、修改时间 | 覆盖（有缓解项） |
| 在写入诱饵资料时尝试覆盖隐蔽区 | 覆盖（保护窗口 + 分配器约束） |
| 断电/崩溃后要求数据不损坏 | 覆盖（WAL 原子事务） |
| 持续监视每次写入的扇区集合（在线流量分析） | **不覆盖**（任何隐蔽卷方案都无法对抗） |

## 2. 公开研究依据

本设计不是凭空构造，而是对几条成熟研究路线的工程化组合：

1. **Canetti, Dwork, Naor, Ostrovsky, *Deniable Encryption*, STOC 1997**
   形式化了"存在多个解密口径、对手无法判定哪一个是真实口径"的可否认加密概念。本项目的双头部槽位（同一口令可解释外层，另一口径解释隐蔽卷）即这一思想在存储场景的落地。

2. **TrueCrypt（2004 起）及其后继 VeraCrypt 的 hidden volume 机制**
   工业界最知名的隐蔽卷实现：外层卷尾部预留区域存放隐蔽卷，外层挂载时通过"保护"避免覆盖。本项目的"尾部隐蔽区 + 受保护挂载（protected mount）"直接沿用这一经过长期检验的布局。TrueCrypt 安全审计（*Open Crypto Audit Project*, 2014–2015）与 VeraCrypt 审计（QuarksLab, 2020）确认了该机制的有效性，同时指出了其对在线/快照攻击的固有脆弱性。

3. **Anderson, Needham, Shamir, *The Steganographic File System*, 1998**
   提出"整个磁盘看起来随机、空闲块与密文块不可区分"的隐写文件系统思想。本项目对全容器做随机填充、空闲区擦洗（churn），正是为了让空闲块与密文块在统计上不可区分。

4. **McDonald, Kuhn, *StegFS: A Steganographic File System for Linux*, 1999**
   在真实文件系统层实现隐蔽数据，并讨论了多快照对比对隐蔽层的威胁。本项目 §7 对快照攻击的诚实警告与 churn 缓解即源于此。

5. **Halderman et al., *Lest We Remember: Cold Boot Attchs on Encryption Keys*, USENIX Security 2008**
   说明了内存中密钥残留的风险。本设计在每次使用后用 `denc_explicit_bzero`（volatile 存储，防止编译器优化消除）清密钥，头部包裹的数据密钥（KEK/DEK 分离）缩短了口令派生密钥的暴露窗口。

6. **文件系统日志（journaling）与写前日志（write-ahead logging）**
   崩溃一致性的标准技术（参见 SQLite WAL、ext3/ext4 journal、ARIES 恢复算法，Mohan et al. 1992）。本项目用双 WAL 槽位 + 提交头最后落盘 + 双超级块，实现全有或全无的事务与 redo 恢复。

7. **原语标准**
   ChaCha20（RFC 8439）、HMAC-SHA-256（RFC 4231）、PBKDF2-HMAC-SHA-256（RFC 8018 / RFC 7914 测试向量）、SHA-256（FIPS 180-4）。所有原语均以标准测试向量（KAT）验证。

## 3. 整体架构

```
                       口令 (password)
                            │ PBKDF2-HMAC-SHA256, 200k 轮, 随机 salt
                            ▼
                          KEK
              ┌─────────────┴─────────────┐
              ▼                           ▼
       头部槽位 0（外层）            头部槽位 1（隐蔽）
       包裹外层数据密钥 DEK_o        包裹隐蔽数据密钥 DEK_h
              │                           │
              ▼                           ▼
   ┌───────────────────────────────────────────────┐
   │  容器文件（固定大小，创建时全随机填充）           │
   │                                                 │
   │  [SB A][SB B][WAL 0][WAL 1][bitmap][inode][data]│ 外层卷
   │                                      ┌──────────┤
   │                                      │ 隐蔽卷    │ 尾部隐蔽区
   │                                      │ 独立的     │ base_sector 偏移
   │                                      │ SB/WAL/…  │
   └───────────────────────────────────────────────┘
```

### 3.1 加密扇区层

- 每个 4096 字节扇区用 ChaCha20 独立加密，nonce = `绝对扇区号 || 域标签`。
- **按绝对扇区号取 nonce** 保证：同一明文在不同位置产生不同密文；外层与隐蔽卷的物理扇区永不共享 keystream。
- 域标签（外层=1、隐蔽=2、头部=3）提供额外的上下文分离。
- 没有任何扇区以明文落盘，包括元数据（超级块、WAL、位图、inode 全部经加密层）。

### 3.2 双头部槽位

容器前两个扇区是两个独立的加密头部：

- 槽位 0：外层卷头部，含 `DEK_o`、卷大小、隐蔽区起始位置（`hidden_start`）。
- 槽位 1：隐蔽卷头部，含 `DEK_h`、隐蔽卷大小。
- 头部整体加密，外层包裹随机填充；无隐蔽卷时槽位 1 保留容器创建时的随机字节。

**可否认性关键**：没有口令时，一个有效的加密头部和一段随机数据在统计上**无法区分**——两者都是高熵字节串。头部不使用任何固定魔数作为明文标记（魔数位于加密载荷内部，需口令解密后才可见），因此对手无法通过扫描特征判断槽位 1 到底是隐蔽头部还是随机填充。

## 4. 对每个具体威胁的处理

### 4.1 诱饵写入不能覆盖隐蔽资料

这是 TrueCrypt 式隐蔽卷的经典难题，有两种失败模式，分别处理：

**(a) 分配器把外层数据块分配到隐蔽区。**
外层头部记录 `hidden_start`。用外层口令挂载时进入**受保护挂载**：文件系统超级块写入 `forbidden_from..forbidden_to` 禁止窗口，分配器 `fs_alloc_blocks` 在扫描空闲块时跳过该窗口的每个块，越界即返回 `NOSPACE`。测试中即使写入远超外层可用容量的数据，也只会得到"空间不足"，绝不会触碰尾部。

**(b) 隐蔽卷与外层卷的物理位置重叠。**
隐蔽卷的磁盘对象持有 `base_sector`（= 外层数据区尾部偏移），所有隐蔽卷 I/O 在卷相对扇区之外再加该偏移，映射到容器尾部的独立物理区域。两层各有独立的数据密钥和 nonce 域，物理与密码学双重隔离。

### 4.2 磁盘空闲区域泄露

- 容器**创建时逐字节随机填充**，不存在零块或可识别的"未使用"图案。
- 文件删除只清位图/inode，数据块位置被标记空闲；`churn` 命令用 CSPRNG 重新随机化所有空闲块，使"曾经写过又删除"的块与"从未使用"的块不可区分（对应 Anderson 1998 / StegFS 的思路）。
- 分析器实测：全容器零全零扇区数为 0，空闲块与密文块熵值同为 ~8.0 bit/byte。

### 4.3 文件修改时间泄露

容器是一个普通文件，宿主文件系统维护它的 mtime/atime。`-k` 选项在会话开始时记录时间戳、关闭时用 `futimens` 还原，使一次挂载/写入不改变容器对外呈现的时间。需要注意：`ctime` 在多数系统上不可由用户重置，这是宿主 OS 的固有限制，文档如实告知。

### 4.4 存储大小变化泄露

容器大小在创建时固定，所有操作（含隐蔽卷）都在预分配区域内进行，**永不扩容、不产生稀疏洞**。实现刻意用 `fwrite` 写满每个字节而非 `ftruncate` 造空洞，避免 `fiemap`/`du` 暴露未分配区段。分析器确认容器大小恒为扇区整数倍且无零洞。

### 4.5 多快照对比泄露（重点，见 §7）

### 4.6 断电不损坏

见 §5 的 WAL 事务设计。故障注入测试在提交的三个阶段分别 `_Exit` 模拟断电，全部干净恢复。

## 5. 崩溃一致性：写前日志（WAL）

每个文件系统操作（put/rm/unlink）拆成若干**原子事务**：

```
提交序列（崩溃点编号对应故障注入）：
  1. 写所有 [旧镜像 | 新镜像] 条目到 WAL 槽位，flush        ← 崩溃点 1
  2. 最后写 WAL 提交头（含序号、目标扇区表、SHA-256 校验和），flush
                                                            ← 崩溃点 2
  3. 把新镜像应用到各"主"扇区，flush                        ← 崩溃点 3
  4. 交替推进双超级块（A/B，带单调序号），flush
  5. 清空当前 WAL 槽位
```

恢复规则（`wal_recover`）：

- 提交头未落盘（崩溃点 1）：日志校验和不通过或无魔数，**丢弃**，主扇区保持旧状态 → 事务从未发生。
- 提交头已落盘但未应用完（崩溃点 2/3）：校验 SHA-256 通过后 **redo**，把新镜像重写到主扇区，再推进超级块、退休日志。
- 双超级块取序号更高且校验通过者，保证超级块本身的更新也是原子的。
- 每次 flush 在 macOS 上用 `F_FULLFSYNC`、其他平台 `fsync`，强制落到物理介质而非页缓存。

测试证明：在 inode 提交（最后一个事务）后断电，恢复后文件完整出现且内容字节一致；在更早事务断电，文件原子性地完全不出现，既有数据不受影响。

## 6. 取证分析器（denc-forensic）

分析器**不持有任何口令**，只使用对手能获得的证据，刻意保持保守和诚实：

- **香农熵 / 卡方均匀性检验**：逐区域计算，卡方 p 值低于 0.01 才判定非随机（避免把随机数据天然含有的少量零字节误报为异常）。
- **重复扇区扫描**：唯一 nonce 下的密文不应出现重复 4K 扇区。
- **全零扇区/稀疏洞扫描**：检测零填充或稀疏文件泄露。
- **头部槽位检查**：报告 salt/迭代次数字段，但明确指出无口令时密封头部与随机填充不可区分。
- **元数据检查**：大小是否扇区对齐、时间戳异常。
- **双快照 diff**：定位变化扇区、变化范围、新字节熵，并指出尾部集中写入这类可疑模式。

### 实测结论

对一个含隐蔽卷且经过外层填充、churn 的容器，分析器输出：

> *No statistical or structural evidence of a second volume. Every region is consistent with either ciphertext or keyed random fill. A hidden volume, if present, CANNOT be proven from this image alone.*

即：**静态镜像无法证明隐蔽卷存在**——这是可否认性成立的核心证据。

## 7. 诚实的根本局限：快照与在线攻击

可否认加密在学术上从未声称能对抗"看到多次磁盘状态"的对手，本项目也不例外。

**快照 diff 实测**：在两次快照之间只做一次隐蔽写入、不做任何外层活动时，分析器能观察到尾部一段扇区发生了变化（虽然新字节仍是高熵、无法解密、无法判定是隐蔽卷还是空闲区擦洗）。变化扇区的**位置聚集**本身构成可疑信号。这与 StegFS（McDonald & Kuhn 1999）和 VeraCrypt 审计报告指出的局限一致。

缓解措施及其边界：

- **churn（空闲区随机化）**：在外层制造遍布整个数据区的随机变化，把隐蔽写入淹没在噪声中。实测 churn 后 diff 显示 430 个扇区在大范围（sector 717..1859）随机变化，尾部聚集特征消失，分析器只能给出"与加密写入或空闲擦洗均一致，无法证明"的结论。
- **操作纪律（无法由代码强制）**：隐蔽卷只应在安全环境、离线时访问；每次隐蔽访问前后配合外层诱饵活动和 churn；避免在被持续监视的设备上写隐蔽卷。
- **不可对抗在线监视**：若对手能实时记录每次写入的扇区集合，任何把数据藏在同一介质的方案都会暴露写入位置。对抗这种对手需要把隐蔽数据放在对手无法观察写入的通道，超出本工具范围。

换句话说，本工具保证的是**"无法证明"**而非"无法怀疑"。可否认性的目标是让持有者在交出外层口令后，对一切疑点都有合理的替代解释（"那只是随机空闲块 / 我做过安全擦除"），而不是让隐蔽操作不留任何痕迹。

## 8. 关键工程取舍

- **自研原语 vs 调库**：为满足"用 C 实现"且无外部依赖，ChaCha20/SHA-256/HMAC/PBKDF2 全部手写，但每个都用 RFC/FIPS 官方 KAT 锁定正确性。实现中曾出现 SHA-256 端序、ChaCha20 对角轮索引、PBKDF2 块索引端序等典型错误，均由 KAT 捕获——这正是不盲目信任自研密码代码的理由。
- **KEK/DEK 分离**：口令经 PBKDF2 只派生出包裹密钥 KEK，真正加密数据的 DEK 随机生成并存在头部里。改口令只需重裹头部、无需重加密整个卷（`chpass` 同时重裹外层与隐蔽两个头部）。
- **WAL 槽位容量**：单事务最多 63 个扇区；大文件按此窗口分批提交，每批仍是原子的，兼顾事务内存开销与崩溃粒度。
- **密钥清零**：所有密钥缓冲在作用域结束时经 volatile 写清零，缓解冷启动/内存交换残留。

## 9. 目录与构建

```
crypto/    ChaCha20, SHA-256/HMAC, PBKDF2, CSPRNG（含 KAT）
include/   公共头与磁盘/文件系统格式
src/       加密扇区层(disk)、WAL 文件系统(fs)、卷管理(vol)、CLI(main)
analyzer/  取证分析器（不链接实现代码、不持有口令）
tests/     密码学 KAT 与 27 项端到端/崩溃/取证测试
```

```
make            # 构建 denc 与 denc-forensic
make selftest   # 密码学标准向量
make test       # 完整测试套件
```

### 常用命令

```
# 创建（-H 指定隐蔽卷大小）
denc create -s 8M -H 2M -p pwfile vault.denc
# 外层受保护挂载（诱饵）
denc open -p pwfile vault.denc put hostfile name.docx
# 隐蔽卷挂载
denc open --hidden -p pwfile vault.denc put secret name
# 空闲区擦洗
denc open -p pwfile vault.denc churn
# 取证（无口令）
denc-forensic audit vault.denc
denc-forensic diff snap0.denc snap1.denc
```
